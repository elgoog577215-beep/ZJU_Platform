## Context

当前 `project_cards` 是长期项目真源，`competition_works` 是单届赛事作品与评审快照。项目广场在带 `competition` 参数时已经能混合展示关联项目和未关联历史作品，但默认 `/projects` 只查询 `project_cards`；本地上一届赛事有 20 条已审核公开作品、姓名、专业、GitHub、奖项和排名完整，却没有 `project_id`，也没有独立的部署链接字段。

本次涉及 SQLite schema、项目/赛事 API、两个投稿表单、项目广场信息架构和历史数据投影。必须保持用户所有权真实、审核状态有效、公共字段可控，并避免把历史作品批量挂到管理员名下。

## Goals / Non-Goals

**Goals:**

- 让未关联的已审核公开赛事作品进入默认项目广场，使上一届 20 个作品完整可发现。
- 把 `/projects` 重构为跨届黑客松项目中心，同时保留项目广场的独立路由与长期项目能力。
- 在长期项目和赛事快照中分别持久化公开部署平台与部署链接。
- 让新投稿明确采集姓名、专业、GitHub、魔搭部署链接，并沿用所有权、审核和赛事排名边界。
- 对桌面、移动端、中英文、链接安全与数据库迁移提供可回放验收。

**Non-Goals:**

- 不自动创建 20 个由管理员所有的长期项目。
- 不根据姓名、标题、GitHub 或专业自动认领作品。
- 不修改黑客松成果页的沉浸式四屏视觉结构。
- 不在本次变更中设计完整团队成员协作、项目孵化 CRM 或生产数据库自动发布。

## Decisions

### 1. 默认广场使用双真源公共投影，不复制历史作品

`GET /api/projects` 在无 `competition` 参数时返回：

1. 已发布的 `project_cards`；
2. 已审核、公开、未删除，且没有指向已发布项目的 `competition_works` 投影。

历史作品的稳定详情仍指向赛事成果深链，不伪装为可编辑 `project_cards`。当作品以后关联到已发布项目时，查询中的 `NOT EXISTS` 自动消除历史投影，避免重复卡片。

替代方案是批量生成项目名片，但会把所有权错误写给补录管理员，且将同一事实复制到两个表，因此不采用。

### 2. 仓库与部署使用独立字段

两个实体都新增：

- `deployment_provider`: 归一化平台标识，当前 `modelscope`，未知平台允许 `other` 或空值；
- `deployment_url`: 对外公开的 HTTPS 部署地址。

`repo_url` / `git_url` 继续代表源码仓库。后端分别校验 URL，不从域名隐式改写 GitHub 字段。前端对魔搭表单默认写入 `modelscope`，未来可扩展而无需再迁移 URL 语义。

### 3. 历史作品维持“赛事归档”身份

历史投影序列化补充 `author`、`major`、部署信息和赛事元数据，前端以“赛事归档”而不是“项目发起人”呈现。GitHub、部署链接直接从赛事快照打开；无部署链接时显示可理解的“部署链接待补充”，不产生假链接。

### 4. 项目广场首页按用户任务重排

首屏结构为：

1. 黑客松项目中心定位与一条主行动；
2. 当前赛事/历届成果摘要；
3. 搜索、赛事筛选和项目内容；
4. 已登录用户的发布/提交入口。

已有卡片、详情、分享、筛选和赛事模式组件继续复用。赛事上下文保持 query-backed，移动端保持单列和 `100dvh` 弹层。

### 5. 投稿仍区分参赛者和运营者

普通用户创建项目后提交赛事快照，作品默认进入既有审核规则；管理员可补录没有 `project_id` 的历史作品。专业属于单届作品公开资料，部署信息同时进入长期项目和当届快照；名次与奖项仍只由运营者维护。

## Risks / Trade-offs

- [默认广场同时查询两类实体，排序和分页更复杂] → 先在 SQLite 查询后合并稳定公共形状，并增加覆盖总数、搜索、赛事筛选和分页的后端测试。
- [历史作品没有可编辑所有者] → 明确标记赛事归档，详情回到赛事成果；认领仍通过身份关系人工确认。
- [部署地址可能失效或指向任意站点] → 仅接受 HTTPS，外链使用安全属性；本次不宣称平台已验证运行。
- [项目与赛事快照的部署信息可能后来不同] → 两者各自保存事实；新投稿取项目值作为默认快照，后续赛事事实不反向覆盖长期项目。
- [默认混合流可能增加响应体] → 维持现有分页上限并只返回卡片所需公共字段。

## Migration Plan

1. 通过 `runMigrations` / `ensureCoreSchema` 幂等增加四个可空列和必要索引。
2. 先运行迁移测试与临时数据库回放，确认旧库可升级、新库可初始化。
3. 更新 API 与前端；本地数据库启动迁移后核对 20 条历史记录数量与字段不变。
4. 生产发布前单独备份数据库，再启动一次幂等迁移；不批量填充部署链接。
5. 回滚前端/API 时保留新增可空列；无需删除列。若公共混合流异常，可关闭默认历史投影而不删除赛事作品。

## Open Questions

- 上一届 20 个作品的魔搭部署链接目前没有数据来源，本次只建立字段和补录入口；真实链接由参赛者或运营者后续补充。
- 历史作品的正式认领交互继续复用现有身份 claim 能力，本次只保证不伪造归属，不扩张为新的认领系统。
