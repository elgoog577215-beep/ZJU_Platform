# 提案：统一用户、权限与组织主体系统

## 背景

当前项目已经有登录账号、个人主页、身份认证、组织 profile、生态伙伴、活动归属、投稿审核和后台用户管理，但这些能力分散在不同入口里。用户真正想要的不是再补一个孤立功能，而是把旧能力重新吸收和整理成一套清晰的用户系统：

- 账号可以是普通用户，也可以承载组织/官方组织的运营身份。
- 权限分为普通、免审核、管理员三档；它们是能力，不应和主体身份混在一起。
- 官方组织既可以作为活动聚合筛选项，也可以作为关于页、黑客松页、合作方墙等前台展示资源。
- 后台需要同时看见账号、权限、组织主体和组织成员关系，而不是只改账号角色。

## 目标

- 在后端补齐账号主体类型与发布审核权限字段，并保持旧 `role` 兼容管理员访问控制。
- 扩展当前用户总览接口，让个人中心能展示“我是谁、能做什么、管理哪些组织、有哪些待处理事项”。
- 新增后台组织治理聚合接口，复用 `profiles`、`profile_members` 与 `ecosystem_partners`，让用户管理页能看见组织主体。
- 重做个人中心的 owner 视图，使它成为饱满的账号与组织工作台。
- 升级后台用户管理，把账号管理、权限管理和组织管理合并成一个清晰运营界面。
- 同步维护中英文用户可见文案。

## 非目标

- 不重写登录、注册和 token 存储策略。
- 不迁移历史活动归属，不改已有活动归属规则。
- 不删除 `ecosystem_partners` 管理能力；本轮只把它的组织治理能力接入用户管理心智。
- 不引入复杂 RBAC、权限矩阵或多租户隔离。
- 不强制要求组织入驻审批流完整上线。

## 数据和 API 影响

- `users` 增加 `account_type`、`review_permission`、`admin_scope` 字段：
    - `account_type`: `personal` 或 `organization`。
    - `review_permission`: `normal`、`trusted` 或 `admin`。
    - `admin_scope`: 管理员范围，当前默认 `platform`。
- `GET /api/users/me/overview` 增加权限、账号类型、组织工作台和下一步建议。
- `GET /api/admin/users` 返回账号类型、发布审核权限、组织数量和内容状态摘要。
- `PUT /api/admin/users/:id` 允许管理员修改 `account_type`、`review_permission`、`admin_scope` 和旧 `role`。
- 新增 `GET /api/admin/user-organizations`，返回组织 profile、合作方展示层级、成员和内容统计。

## UI 影响

- 个人中心 owner 首屏改为账号与组织工作台，展示权限档位、资料完整度、组织主体、内容状态、成果认领和快捷动作。
- 后台用户管理增加分段视图：账号、组织主体、权限治理。
- 用户表格展示账号类型、发布权限、关联组织和待审核内容。
- 组织表格展示 profile、合作方层级、成员、活动/内容统计和跳转到组织主页。

## 风险和回滚

- 风险：旧数据库缺少字段时可能导致启动或列表报错。处理方式是在 migration 中使用 `ensureColumns` 补齐字段，并给旧账号回填默认值。
- 风险：权限字段和旧 `role` 可能语义重叠。处理方式是保留 `role = admin` 作为后台访问判断，同时让 `review_permission = admin` 只作为发布审核能力的表达。
- 回滚：字段为向后兼容新增字段，不删除旧字段；若前端需要回滚，可继续使用旧 `/admin/users` 返回中的 `role`。
