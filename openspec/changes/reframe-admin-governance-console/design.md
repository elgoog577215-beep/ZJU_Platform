# 设计：后台生态运营与治理控制台

## 核心判断

后台混乱的根因不是视觉风格，而是后台没有用同一套业务地图解释所有管理对象。新的后台结构应围绕“拓浙 AI 生态”的运营动作组织，而不是围绕历史组件名称组织。

稳定业务主线是：

- 赛事选才。
- 项目育人。
- 社区聚人。
- 产学就业闭环。

后台要把这四条主线翻译成可管理对象：内容、主体、项目、AI 能力、系统审计。

## 目标导航域

### 运营总览

负责今日待办和系统状态，不承载深层编辑：

- 审核待办。
- 内容资产状态。
- 主体关系异常。
- 生态项目状态。
- AI 能力健康。
- 最近高风险操作入口。

### 内容与审核

负责所有公开内容的创建、审核、下架、恢复和分类：

- 活动。
- AI 社区统一内容。
- 文章、新闻、图片、视频、音频。
- 页面内容。
- 标签和影像分类。

项目广场是否放在这里取决于后续实现。如果只做公开内容审核，可进入内容与审核；如果承担项目育人运营，应进入生态项目运营。

#### 内容采集工作台

学校通知聚合是平台的内容供应链，不应继续被呈现为“输入 token、fakeid 和延迟参数”的爬虫工具页。界面需要客观呈现的稳定对象是：

- 学院、社团等公众号来源。
- 微信连接与定时采集状态。
- 最近采集记录。
- 等待审核的候选内容。
- 连接诊断与单次采集工具。

因此内容采集页使用“概况、采集源、候选内容、连接与工具”四个工作区。默认首屏在一行集中显示来源数量、连接状态、调度状态和本轮新增，正文直接展示最近采集与候选内容；不使用编号、箭头、“下一步”或流水线来规定管理员的操作顺序。登录诊断、单次抓取、token、fakeid、分页间隔与风控参数只在相应工作区或折叠区出现。

当前实现边界必须明确：现有服务支持的是学院、社团等主体运营的微信公众号来源。它还不是任意学校网站、多平台账号或通用网页爬虫。未来新增学院网站等连接器时，后台业务仍需共享来源、运行、候选、修正和发布状态合同，但该合同不得被前端强行渲染为线性步骤；不同来源类型需要独立定义抓取策略、失败原因和恢复机制。

### 主体与关系

负责“谁拥有、谁发布、谁背书、谁有权限”：

- 账号。
- 组织 profile。
- 组织成员。
- 发布审核权限。
- 后台访问角色。
- 生态/比赛合作方与活动提供方。
- 历史活动归属迁移。

这里必须遵守既有三轴模型：

- `account_type`：个人或组织账号主体。
- `review_permission`：普通审核、免审核、管理员级发布能力。
- `users.role='admin'`：后台访问。

合作展示必须继续使用 `ecosystem_partners.partner_scope`，不能用组织存在或活动数量推断合作身份。

### 生态项目运营

负责平台最能体现生态价值的运营对象：

- 黑客松报名、作品、媒体和成果。
- 项目广场项目卡片、状态和下架。
- 未来学习中心或产学项目需求。
- 后续企业/政府需求、学生团队承接和成果认证。

当前缺口是项目广场没有一等后台入口。

### AI 能力治理

负责 AI 能力是否可运行、是否可信、是否有质量闭环：

- 模型 key 与 provider。
- 活动元数据治理建议。
- AI Agent 成熟度与缺口。
- 搜索索引覆盖。
- 推荐质量评测。
- 运行健康、失败率和最近运行。

命名上应避免“全能 AI 治理”。没有接入或只读诊断的模块必须标注“实验性”“待接入”或“只读诊断”。

当前实现将页面分为“能力状态、活动元数据、模型配置”三个工作区。能力状态以单行状态和模块列表表达，并明确属于只读诊断；活动元数据保留扫描、选择和应用闭环；模型配置前置基础设施提示，避免 Key 数量被误解成 AI 业务效果。

### 系统与审计

负责低频但高风险的后台能力：

- 站点设置。
- 留言反馈。
- 数据备份。
- 审计日志。
- 高风险批量操作记录。

站点设置属于低频配置，不应把安全、外观、关于页几十个字段同时平铺。一级按“基础与安全、公共外观、关于站点”收纳；关于站点再按团队身份、数据依据、AI 社区、浙客松、支持网络和结尾分区，每次只显示一个内容区块。

## 模块状态表达

后台总览和当前模块顶部可显示状态：

- `可运营`：已有稳定数据、操作入口和验证。
- `维护中`：功能可用但需要合并、i18n 或测试补齐。
- `实验性`：AI 或自动化能力尚未形成完整闭环。
- `仅工具`：内部维护工具，不应被误解为核心业务模块。

第一阶段可以先用静态配置表达状态，后续再由 API 或运行数据驱动。左侧导航保持静态分组和两列模块入口，不在每个入口附加数量、状态标签或折叠层级；状态只在用户进入模块后出现。

## AI 治理边界

当前 `AiAssistantManager` 应被解释为早期 AI 能力治理面板，而不是全站 AI 大脑。它应保留：

- Agent 体系完成度。
- 活动治理扫描与应用。
- 模型配置管理。

但需要调整呈现：

- 活动治理是“活动元数据治理”，不是泛 AI 治理。
- 模型 key 是基础设施，不是主要业务成果。
- Agent 缺口是诊断，不是已完成能力。
- 搜索索引、推荐评测、内容解析等可显示为待接入或只读状态，但不能制造不可操作入口。

## 项目后台缺口

项目广场已经是前台一等页面，也有 admin takedown API，但后台没有一等管理视图。后续应补：

- 项目列表。
- 状态筛选。
- 举报/下架。
- 作者与组织归属。
- 项目需求标签和技术栈。
- 与个人/组织主页聚合的跳转关系。

第一版不新增私信、动态订阅或复杂项目流程。

第一版项目治理复用 `project_cards`、`project_reports`、`profiles/profile_members` 和 `audit_logs`：后台列表可按状态、进度和关键词筛选，显示举报数量、最近举报原因、发起人及关联组织，并支持带原因下架和恢复。下架与恢复写入审计日志，不新增第二套项目状态表。

通用图片、视频和音频仍归入“内容与审核”；只有带明确 `event_key`/比赛关系的成果资产才由浙客松领域拥有。当前导航不把所有媒体资产复制进赛事域，后续赛事媒体关系继续由 `rescue-hackathon-outcome-architecture` 收束。

## i18n 策略

本轮不做全后台一次性文案搬运。原则是：

- 被改造的模块必须同步中英文。
- 新增模块状态、导航域、空状态和错误提示必须进入 locale。
- 未触碰模块的硬编码文案先作为债务记录，不用制造巨大 diff。

## 验证策略

第一阶段：

- `npm run openspec:validate`
- `git diff --check`

进入前端实现后：

- `npm run lint`
- `npm run build`
- `npm run test:e2e -- e2e/admin-console.spec.js --project=chromium`
- 中英文后台关键页面检查。

如果新增项目后台 API：

- 后端语法检查。
- 项目下架/恢复 smoke。
- 权限校验 smoke。
