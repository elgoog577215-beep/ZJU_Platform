## Context

当前三条链路已经分别存在：

- `project_cards` 是用户长期维护的项目对象，拥有广场、详情、收藏、举报、profile 聚合和分享海报。
- `competitions + competition_works` 是赛事成果档案，拥有投稿、审核、名次、奖项、作品故事和成员身份绑定。
- `photos / videos + competition_media_links` 是赛事现场媒体真源，影像库按赛事聚合展示。

缺口不是再建一套页面，而是缺少项目与赛事作品之间的一等关系，导致黑客松、项目广场和影像库只能靠 URL、标题或运营者记忆跳转。用户从黑客松提交作品时还要重复填写项目名称和介绍，项目详情也无法证明参加过哪场赛事。

本变更同时涉及数据库、公开 API、投稿交互、三页信息架构、分享海报和中英文，因此以跨模块 OpenSpec 实施。现有赛事成果页与影像库的黑绿 X-field 视觉是已确认基线；项目广场在同一视觉世界内强化，不改全站 Navbar、Logo 和其他公共页面。

## Goals / Non-Goals

**Goals:**

- 让一个长期项目可参加多场黑客松，每场比赛保留独立作品快照、审核与荣誉。
- 让用户从黑客松进入项目广场，选择已有项目或先建项目，再提交到当前赛事。
- 让赛事作品、项目详情和现场影像双向可追溯，并把赛事上下文写进 URL。
- 让项目广场在通用发现模式与赛事现场模式之间共用同一页面和项目真源。
- 强化项目海报的赛事证明与扫码回流，同时守住公开信息和联系方式边界。
- 保持历史作品、旧链接、未关联记录和现有审核流可用。

**Non-Goals:**

- 不把 `competition_works` 合并进 `project_cards`，也不让名次、奖项和审核状态成为项目字段。
- 不根据标题、作者、标签或 Git URL 自动关联历史项目。
- 不删除 `competition_media`、`competition_works` 或任何上传资源。
- 不新增私信、队伍管理、评委打分、票务、积分或完整赛务系统。
- 不重做个人/组织数字名片；名片仍然只投影 profile 公开事实。

## Decisions

### 1. `project_cards` 是项目真源，`competition_works` 是赛事快照

为 `competition_works` 增加可空 `project_id` 外键与 `(competition_id, project_id)` 部分唯一索引。赛事提交保存标题、简介、作者、封面、Git、故事和奖项等当时快照；项目后续修改不会重写历史赛事记录。

选择显式外键而不是标签/标题匹配，是因为同名项目、改名、多人署名和多次参赛都无法用文本稳定判定。选择把关系放在作品表而不是项目表，是因为一张作品记录只属于一场赛事，而一个项目可拥有多个赛事记录。

### 2. 新投稿必须显式选择项目，历史与管理员录入允许未关联

普通用户提交 `work` 时必须提供自己拥有的 `project_id`；后台管理员为了兼容历史补录可以不关联。后端校验项目存在、归属当前用户、未下架，并阻止同一项目重复提交同一赛事。

项目可以是草稿或已发布，但公开赛事成果只在关联项目仍为 `published` 时返回公开项目深链；项目被下架不会删除赛事作品，只隐藏项目回流入口。这避免治理动作破坏历史赛事事实。

### 3. 项目广场用 URL 进入赛事模式，不创建第二广场

通用入口继续是 `/projects`。从黑客松或影像库进入时使用 `/projects?competition=<slug>`：

- 顶部显示当前赛事标题、日期、作品数和“提交本场作品”。
- 列表只展示已审核且显式关联该赛事的项目。
- 用户可一键回到全部项目；筛选、收藏、详情和分享沿用原能力。
- 新建项目完成后直接打开当前赛事投稿弹层，并预选新项目。

这比新增 `/hackathon/projects` 更能守住项目广场的唯一入口和页面历史。

### 4. 公共 API 返回白名单赛事摘要，不暴露审核或身份内部字段

项目列表和详情增加 `competitions` 摘要：`slug`、`title`、`event_date`、`work_id`、公开 `award/rank`。赛事成果作品增加 `project_id`、`project_title`，仅在项目已发布时返回。联系方式、审核备注、身份 claim 和内部关联状态不进入公共响应。

列表的赛事关系由后端批量查询后按项目分组，避免每张卡发一条请求；`competition` 筛选直接通过 join/exists 完成，避免前端下载全部项目再猜测。

### 5. 投稿弹层复用现有成果入口，增加项目选择器

`CompetitionOutcomeUploadModal` 继续处理照片、视频和作品。作品类型加载 `mine=1` 的当前用户项目，提供选择已有项目与“去项目广场创建”入口；由项目广场打开时可传 `initialProjectId`。切换上传类型时保留赛事上下文，不跨赛事提交。

### 6. 三页共享现场世界，但承担不同任务

- 黑客松：比赛叙事、规则、作品与荣誉，主行动指向“用项目参赛”。
- 项目广场：作品/项目发现、提交、协作和长期维护；赛事模式以一张开放式计分牌和不对称作品墙呈现，不堆指标卡。
- 影像库：现场证据；提供“看本场作品”和“进入本场项目广场”，不承载项目编辑。

项目广场沿用赛事成果页已有 X-field、酸性绿、黑绿底、纪实图片和线性编号，首屏直接呈现当前赛事与提交行动。昼间模式使用高对比纸白/墨黑/深绿，不把现场模式降成普通浅色卡片。移动端纵向叙事，只有赛事切换轨可横向滚动；弹层使用 body portal、`100dvh`、scroll lock 和返回关闭。

### 7. 项目海报是传播投影，不是存储对象

项目海报从项目详情响应读取赛事摘要，在有关联时显示最新/当前赛事、奖项或参赛状态，并继续用二维码指向项目详情。详情页再提供到赛事与影像库的深链。海报不写联系方式，不保存为新数据库记录，不复制项目或赛事事实。

### 8. 现场感由作品、比例和一个主行动承担，不由控制项数量承担

第二轮视觉收束不删除业务能力，但减少同屏竞争：

- 赛事项目广场首屏只保留赛事身份、日期/入选数、一个“提交参赛项目”主行动；创建项目作为投稿流程内的备用路径，不再与投稿并列抢占首屏。
- “赛事现场 / 影像档案 / 全部项目”合并为轻量文本路径，不再各自做成按钮卡片。
- 搜索、排序、进度与需求筛选合并为一条控制带；赛事模式默认只露出搜索和排序，进阶筛选按需展开。
- 赛事作品卡以封面、标题、奖项、发起人和收藏为必要信息；技术标签、需求标签和浏览量不在赛事墙重复铺陈，仍可在详情查看。
- 影像库首屏保留上传主行动，项目广场作为唯一跨页次行动；赛事作品通过项目广场进入，避免三个并列按钮重复解释同一链路。

现场感继续来自 X-field、真实影像、开放式大比例作品墙、酸性绿信号与单次首屏显影。不得增加卡片套卡片、装饰性玻璃层或对每个区块重复编号。

## Risks / Trade-offs

- [历史作品没有 `project_id`] → 保持未关联可展示；只为新提交强制关联，后台后续可人工治理，不自动猜测。
- [项目删除或下架导致赛事深链失效] → 赛事快照继续展示，公开 serializer 仅移除项目入口；后续如需删除项目，仍由现有治理路径决定。
- [项目标题后续变更与赛事标题不同] → 明确视为正确的历史快照；项目链接展示当前项目名，赛事作品展示提交时名称。
- [项目广场同时承担通用发现与赛事模式，页面复杂度增加] → 以 URL 上下文切换首屏和数据范围，共用卡片、详情和筛选，不建立平行状态树。
- [SQLite 旧库外键行为不一致] → 使用可空字段、幂等 `ensureColumns`、部分唯一索引和应用层校验；不在本轮重建整表。
- [视觉强化影响原有收藏/分享/创建] → 只重排页面壳与赛事标识，保留现有操作函数和深链；用桌面/移动、中英文、通用/赛事两种状态做真实页面回归。

## Migration Plan

1. 幂等新增 `competition_works.project_id` 与查询/唯一索引，不更新历史行。
2. 后端先兼容读取关联字段，再部署写入校验；旧客户端不提交 `project_id` 时，普通用户收到可恢复的 400 提示，管理员补录保持兼容。
3. 部署前端项目选择与三页互链；历史未关联作品继续按旧样式展示。
4. 验证双赛事隔离、重复提交、非所有者拒绝、下架项目隐藏深链、项目广场筛选与海报公开字段。
5. 回滚时可先回退前端入口和后端写入要求；新增可空字段与索引保留，不删除数据。必要时取消部分唯一索引也不影响已有行。

## Open Questions

- 历史作品与项目的人工关联后台可作为后续治理任务，本轮不自动迁移。
- 评审期间是否需要项目 owner 更新参赛快照，当前沿用作品审核流与管理员编辑，不新增参赛版本系统。
