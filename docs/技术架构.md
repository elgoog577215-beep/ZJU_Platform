本文回答“仓库怎样组织、正式数据由谁拥有、主要运行链怎样连接、新能力应该接在哪里”。它不维护产品愿景、实施进度、历史测试数字和具体 OpenSpec 任务。

## 1. 总体结构

```text
React Web / PWA
微信小程序 WebView / Android 包装 / iOS Capacitor
  -> HTTP / JSON / multipart / 原生桥接
  -> Express 安全与接入层
  -> controller + application service + data/config
  -> SQLite / uploads / 任务与索引
  -> AI provider / 微信平台 / Playwright 浏览器
```

| 目录                  | 职责                                                                    |
| --------------------- | ----------------------------------------------------------------------- |
| `src/`                | React 前端、路由、页面组件、Context、客户端 API 与共享 UI               |
| `server/`             | Express 服务、路由、controller、领域服务、SQLite schema、采集与治理脚本 |
| `public/`             | 静态图片、PWA 资源和 locale；当前运行时只启用 `zh`、`en`                |
| `wechat-miniprogram/` | 微信小程序 WebView 壳、登录绑定和原生上传/分享桥接                      |
| `android-twa/`        | Android TWA/WebView 包装、签名与应用配置                                |
| `ios/`                | Capacitor iOS 工程与原生壳配置                                          |
| `e2e/`                | Playwright 桌面、移动、后台和关键流程回归                               |
| `openspec/`           | 高影响变更的提案、设计、正式规格、任务与归档                            |
| `docs/`               | 当前产品、状态、架构、开发禁区、操作指南和历史材料                      |

开发态前端运行在 `5180`，后端运行在 `5181`。本地安装、启动和常用检查命令见 [README](../README.md)；本文件只维护运行边界和系统结构。生产构建由 Express/网关提供，生产后端由 PM2 管理，Caddy 负责 HTTPS、静态与同域应用路由。

## 2. 前端结构

### 2.1 应用壳与路由

`src/App.jsx` 负责 Router、Provider、全局壳层、按路由懒加载、动态 chunk 有界恢复和多端环境判断。

主要页面：

| 路由                                      | 主要职责                             |
| ----------------------------------------- | ------------------------------------ |
| `/`                                       | 首页和生态入口                       |
| `/events`                                 | 活动发现、筛选、详情、报名与 AI 推荐 |
| `/articles`                               | AI 社区统一内容和学习资源            |
| `/projects`                               | 项目广场与项目名片                   |
| `/hackathon`、`/hackathon/works`          | 浙客松赛事与成果                     |
| `/profiles`、`/u/:handle`、`/org/:handle` | 组织目录、个人与组织 profile         |
| `/user/:id/center`                        | 兼容用户中心入口                     |
| `/media`、`/gallery`、`/videos`           | 媒体与记录                           |
| `/about`、`/download`                     | 生态介绍与应用下载                   |
| `/admin`                                  | 生态运营与治理后台                   |

旧 `/community`、`/ai-community` 和部分用户路径通过重定向兼容，不是新的并行产品入口。

`/admin` 由 `AdminDashboard.jsx` 维护统一 tab 合同，并按运营总览、内容与审核、主体与关系、生态项目运营、AI 能力治理、系统与审计六个治理域收纳历史模块。当前模块状态由前端静态配置表达；具体业务数据仍由各领域 controller/service 拥有。

### 2.2 状态与数据访问

- `AuthContext`：登录用户、token 生命周期和微信登录回执。
- `SettingsContext`：主题、站点设置和显示偏好。
- `MusicContext`：跨页面媒体播放。
- `src/services/api.js`：Axios 接入、认证头、错误和有限重试。
- `src/services/platformClient.js`：较新的平台 API 边界。
- `src/hooks/`：SWR 与按领域组合的数据读取。
- 组件本地状态：弹层、筛选、草稿和展示交互，不拥有可持久业务事实。

新代码优先进入 `src/app`、`src/features`、`src/shared` 或明确领域模块。当前仍有大量能力集中在 `src/components` 大组件，采用触及式收口，不一次性搬家。

### 2.3 渲染、主题与国际化

- 当前运行 i18n 支持 `zh`、`en`，入口为 `src/i18n.js`，词典位于 `public/locales/zh` 和 `public/locales/en`。
- 其他 locale 目录是历史资源，不代表当前可对外承诺七语言支持。
- 主题由 `SettingsContext`、`src/index.css` 语义变量和共享 helper 共同控制；白天/黑夜共享组件不能各自复制颜色系统。
- 全屏弹层通过 `src/shared/ui/BodyPortal.jsx` 脱离带 transform 的路由容器，并配合 `100dvh`、scroll lock 和返回关闭。
- `vite.config.js` 配置 PWA、Service Worker、chunk 恢复和同域子应用导航排除。

### 2.4 移动端操作与动效边界

- 移动端顶栏只保留方向和少量即时操作；排序、筛选和结果状态放在内容工具栏；卡片操作贴近对象；低频入口进入 More/Profile。
- 桌面端导航未出现在移动底栏的次级入口，必须在 More 中有可见、可返回的入口；不能留下“代码里有抽屉、用户找不到按钮”的死路。
- 新增动效优先复用共享 motion token 和 CSS utility，优先 `transform`、`opacity` 等合成属性；必须尊重 `prefers-reduced-motion`。
- 这些规则只约束交互和实现边界，不替代具体页面的 OpenSpec、代码状态和实际移动端验收。

## 3. 后端结构

### 3.1 接入层

`server/index.js` 负责：

- 日志、压缩、条件请求和安全响应头。
- Cookie、HPP、输入清理、限流、CORS 和 body 大小。
- `/uploads`、静态构建、assetlinks 与 SPA fallback。
- `/api/health`、统一 `/api` 路由与错误处理中间件。

`server/src/routes/api.js` 统一挂载认证、用户、profile、社区、项目、活动、搜索、上传、微信、AI、比赛、后台和通用资源路由。

### 3.2 应用与领域层

目标分层是：

```text
route -> controller -> application/domain service -> data/config/helper
```

当前成熟度不完全一致：

- AI runtime、活动推荐、profile、搜索索引、微信采集、原生上传等已有独立 service。
- 部分旧 `resourceController`、社区、后台和赛事能力仍在 controller 中直接组合 SQL 与业务判断。
- 新能力不得扩大 controller 直写 schema 和跨域逻辑；触及旧链时逐步向 service 收口。

主要能力模块：

| 能力               | 主要位置                                                                             |
| ------------------ | ------------------------------------------------------------------------------------ |
| 账号与认证         | `authController.js`、`AuthContext.jsx`、`authTokenStorage.js`                        |
| profile 与主体关系 | `profileController.js`、`profileService.js`、`userProfileService.js`                 |
| 内容与审核         | `resourceController.js`、`communityController.js`、`newsController.js`               |
| 活动与推荐         | `eventController.js`、`eventRecommendation/`、`eventIntelligenceService.js`          |
| 项目广场           | `projectCardController.js`、`ProjectManager.jsx`、`projectShareCardService.js`       |
| 浙客松与成果       | `competitionController.js`、`hackathonController.js`、`hackathonTemplateService.js`  |
| 搜索与索引         | `globalSearchService.js`、`resourceSearchIndexService.js`                            |
| AI runtime 与治理  | `unifiedAiRuntimeService.js`、`aiAgentRegistryService.js`、`aiModelConfigService.js` |
| 微信采集           | `wechatMpAdminService.js`、`wechatMpScheduledIngestService.js`、相关 controller      |
| 多端桥接           | `nativeUploadSessionService.js`、`nativePosterSessionService.js`、微信小程序工具     |

## 4. 数据与正式真源

### 4.1 SQLite 与迁移

SQLite 是当前主数据库。schema 由两层共同维护：

1. `server/src/config/ensureCoreSchema.js` 建立核心表。
2. `server/src/config/runMigrations.js` 与 `server/src/config/migrations/helpers.js` 执行幂等补齐和兼容迁移。

这是已经存在的正式迁移入口，但仍保留大量按表检查与 `ALTER TABLE` 的历史兼容块。新 schema 变化进入 config/migrations，不进入 controller 或热请求路径。`seed.js` 不能单独代表当前生产 schema。

数据库、WAL、备份和上传目录是运行数据，均不得进入公开 Git。

### 4.2 领域拥有者

| 领域         | 正式真源                                                                                                                                         | 不能作为真源的对象                      |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------- |
| 账号与认证   | `users`、认证服务和 token 合同                                                                                                                   | 页面本地用户副本、硬编码管理员身份      |
| 公开身份主体 | `profiles`、`profile_members`、`profile_aliases`                                                                                                 | 内容自由文本组织名、单独名片账号        |
| 权限         | `account_type`、`review_permission`、`role/admin_scope`                                                                                          | 一个万能 role、前端隐藏按钮             |
| 合作层级     | `ecosystem_partners.partner_scope`                                                                                                               | profile 类别、logo 是否存在、活动数量   |
| 活动         | `events` 与显式 uploader/publisher/organizer 关系                                                                                                | 微信解析临时对象、AI 推荐回答           |
| 社区         | `articles`、`news`、`community_posts` 的兼容领域合同                                                                                             | CLI、微信、组件本地草稿形成的独立内容池 |
| 项目         | `project_cards`、公开 `deployment_provider/deployment_url` 与发起人/profile 关系                                                                 | 项目分享海报、组队帖、自定义主页卡片    |
| 赛事成果     | `hackathon_schedule_config`、带 `event_key` 的报名、competitions、`competition_works`（含单届仓库与部署证据）、canonical media 与 identity links | 静态作品数组、legacy media UI 投影      |
| 搜索         | 公开已审核业务对象 + `resource_search_index`                                                                                                     | 浏览器缓存、模型临时语义标签            |
| AI 配置      | Agent registry、model config、评测与遥测                                                                                                         | Prompt 展示文案、单次 provider 返回     |
| 微信采集     | ingest account、run 进度与心跳、article、AI 筛选、parse/review 状态                                                                              | 浏览器登录现场、一次性日志              |

## 5. 主要运行链

### 5.1 活动发现与推荐

```text
活动上传或微信解析候选
-> AI 初筛与自动治理候选
-> 审核、类别、学院范围与主体归属
-> 公开 events
-> 搜索/筛选 或 活动推荐助手
-> 收藏、报名、查看与反馈
-> 用户行为和推荐遥测
```

搜索使用用户本次查询；推荐同时消费用户资料、活动事实和行为证据。长期画像在用户系统维护，活动助手不拥有它。

### 5.2 AI 社区发布

```text
网页编辑 / 文档导入 / CLI / 微信公众号采集
-> 统一解析与结构化草稿
-> 上传者和发布主体
-> 审核状态
-> AI 社区统一内容视图
-> 用户主页、搜索、互动与运营后台
```

不同入口可以有专用解析器和上传协议，但发布、审核、归属、恢复和公开规则必须一致。

微信公众号采集在后台通过 `WeChatMpImportManager.jsx` 统一为四个工作区：运行概况、采集源、候选内容、连接与单次采集。默认首屏消费 ingest account、登录健康、调度与 run/article 状态；token、fakeid、分页延迟和风控参数只在高级工作区或折叠区呈现。

当前来源连接器只覆盖学院、社团等主体运营的微信公众号。未来学院网站或其他平台连接器必须复用来源、运行、候选、修正和发布状态合同，但前端不得因此把它渲染成强制线性步骤；新连接器也不能复用浏览器登录现场或把一次性抓取日志升级为业务真源。

### 5.3 项目广场治理

```text
project_cards + project_reports
-> /api/admin/projects 状态、进度、关键词与举报信号
-> 发起用户 + profiles/profile_members 归属
-> 管理员带原因下架或恢复
-> audit_logs
```

项目治理不建立第二套项目表。公开广场仍只读取 `published`；后台读取全部状态，`removed` 恢复时回到 `published`，操作证据由审计日志持有。

### 5.4 主体与归属

```text
users 登录账号
-> profile 创建、认证或成员关系
-> 发布/主办/合作/成员等显式角色
-> 内容、活动、项目与成果归属
-> 公共主页、组织目录和后台治理
```

历史内容迁移先生成候选和证据，再由管理员确认并写审计日志，不复制记录或直接覆盖。

### 5.5 项目与浙客松成果

```text
后台发布赛事日程模板、页面开关、时间轴和动态表单
-> 前台按 event_key 选择当前或历史赛事
-> /hackathon 默认报名并保留成果切换；日程时间决定赛前、赛中、赛后公开阶段
-> 发起、报名、组队或一步投稿
-> project_cards 保存长期项目，competition_works.project_id 保存单届参赛快照关系
-> /projects 混合 published project_cards 与未关联的 approved/public competition_works 归档投影
-> competition_media_links 复用 archive/highlight 角色投影照片直播与赛后精选
-> 后台维护审核、公开名次/奖项和精选关系，不复制项目或媒体
-> /hackathon 赛事现场、/projects?competition=<slug> 当届项目广场、/media?event=<slug> 影像档案互通
-> 项目详情、赛事成果页、profile 和分享海报聚合
-> 分享、收藏、人才和下一次机会
```

赛事日程当前以 `settings.hackathon_schedule_config` 为配置真源，`shared/hackathonTemplateDefaults.json` 只提供代码默认值；发布时同步活动赛事档案和旧设置兼容投影。`project_cards` 是长期项目真源，`competition_works` 是赛事作品快照；两者分别保存仓库地址与可空的 HTTPS 部署地址，不从 GitHub 推断魔搭链接。同一项目可进入多届赛事，但同一赛事内只允许一条有效项目关系。默认 `/projects` 只把未关联已发布项目、已审核、同意公开且未删除的赛事作品序列化为只读“赛事归档”，`user_id` 保持为空；显式关联已发布项目后由查询去重。赛事照片仍存入 canonical `photos`，`competition_media_links.role=archive` 进入最新优先直播流，切换为 `highlight` 后同时进入运营精选，文件和资源行不复制。历史赛事作品不做猜测性项目绑定。项目、比赛、作品和媒体是不同实体，必须通过一等关系连接，不能只靠标签和静态数组拼接。

### 5.6 AI 搜索、推荐与治理

```text
公开正式资源 / 用户画像 / 行为证据
-> shared AI runtime + 专用 Agent/服务
-> 结构化结果、解释与遥测
-> 用户行动或管理员候选
-> 反馈、golden/live 评测与质量治理
```

AI 输出默认是建议、筛选条件或候选。正式内容、主体、权限和迁移仍经过领域 controller/service、审核与权限检查。

### 5.7 多端运行

```text
同一 Web 产品与 API
-> PWA
-> 微信小程序 WebView + 原生桥
-> Android TWA/WebView
-> iOS Capacitor/WKWebView
```

环境判断位于 `src/utils/miniProgramEnv.js`、`wechatMiniProgramBridge.js`、显示模式工具和各壳配置。平台特有上传、分享、登录和返回在同一交互入口内分流。

## 6. 认证、安全与隐私

- JWT 由后端签发；前端默认保存到 `sessionStorage`，只有显式持久化选择才进入 `localStorage`。
- 管理员访问、账号主体和免审核发布是不同权限轴。
- 上传由 Multer、大小/类型限制、会话和后端校验共同控制；前端判断不是安全边界。
- 密钥、Prompt 正文、provider 推理、数据库、用户上传和商业文书不进入日志、前端 bundle 或公开文档。
- 公开 profile 目录只展示允许批量发现的组织主体；个人通过精确链接、作者或用户中心进入。
- 写操作默认不自动重试；确实幂等的写入需要调用方显式声明并提供幂等边界。

## 7. 搜索与 AI 基础设施

- `unifiedAiRuntimeService` 负责 provider 调用、结构化解析、修复和通用遥测。
- `aiAgentRegistryService` 描述 Agent 能力、成熟度和检查入口。
- `aiModelConfigService` 管理模型配置与可用性测试。
- `globalSearchService` 保持统一搜索结果协议，并合并 SQL/业务召回与索引补充召回。
- `resource_search_index.vector_json` 是轻量 token-hash/词元表示，不是真实 embedding。
- 活动推荐按 intent、retrieval、ranking、explanation、response builder 和 telemetry 分层，不与全站搜索合并。

## 8. 部署与运行

### 8.1 本地

本地安装、启动、端口和测试命令以 [README](../README.md) 为入口。本地与生产共用 `/api/health` 健康端点；运行态验证仍需确认进程持续、HTTP 成功和目标页面可见。

### 8.2 生产

`master` 推送触发 `.github/workflows/deploy.yml`：

```text
checkout + Node 20
-> SSH 检查服务器 worktree
-> npm install + Vite build
-> 服务器同步代码、安装后端依赖和 Playwright Chromium
-> PM2 restart + 127.0.0.1:3001 健康检查
-> 上传 dist
-> caddy validate + reload
-> tuotuzju.com 健康、API 与子路由验证
```

生产反向代理是 Caddy，不是 Nginx。流水线、运维文档和故障判断必须以当前监听进程与 Caddy 配置为准。

## 9. 兼容、降级与扩展规则

- 旧路由、旧表和旧内容源可以只读兼容，新的正式写入必须进入当前领域合同。
- 社区统一视图可以暂时读取多表，但新入口不得新增第五套内容池。
- schema 迁移必须幂等、可审计、可备份恢复；请求现场不能临时改表掩盖迁移缺失。
- 模型失败返回明确失败、局部可恢复候选或最后可用结果，不伪造正式业务内容。
- 新增状态前先确认现有拥有者；新增接口前先确认能否扩展稳定领域投影。
- 新增 AI 能力说明输入、输出、持久化、用户控制、质量评测、失败降级和旧入口退出计划。
- 具体字段、状态机、接口和验收场景以当前正式 OpenSpec 为准；架构变化完成后再更新本文，不提前记录设想。
