# 内容采集设计

这是[产品蓝图](../产品蓝图.md)中内容输入与审核业务的展开。它规定采集结果怎样进入正式内容；账号配置、部署、命令和排查步骤见[公众号采集手册](../操作手册/微信公众号文章采集.md)，当前未验证部分见[产品状态](../产品状态.md#内容采集)。

## 内容设计

| 对象           | 表达的事实                                                         |
| -------------- | ------------------------------------------------------------------ |
| 来源与授权     | 公众号/来源标识、入口类型、有效状态、采集配置；凭据保持私有        |
| 采集运行       | 本次范围、游标、进度、心跳、错误、停止与重试状态                   |
| 原文章与缓存   | 来源 ID、原链接、标题、正文、图片、发布时间，以及正文是否就绪      |
| 筛选与提取候选 | AI 初筛、来源依据、提取字段、解析状态、审核结果与正式内容关联      |
| 正式活动/内容  | 经校验和审核的标题、介绍、时间、地点、主办方、来源、配图与发布主体 |

登录、文章发现、正文抓取、字段提取、审核、发布是不同结果。一次登录成功或 HTTP 200 不能说明采集完成；缓存文章和 AI 候选不能冒充已发布活动。

活动面向准备参加的人，正文包含有来源的一句话看点、关键信息、分节说明和必要配图。关键信息表达时间、地点、面向对象、报名方式/截止、名额、费用与收获；未知事实为空，不按组织名称猜活动目的。

## 逻辑设计

### 采集与发布

```text
受信来源与有效授权
  → 发现文章 → 取得真实正文/图片 → 清洗与图片本地化
  → 初筛与字段提取 → 关联或生成审核候选 → 审核 → 正式活动/内容
```

运行状态持久化，失败保留错误和恢复位置，重复输入复用来源标识。相同事件的倒计时、转载、购票与入场说明先检查是否已有活动：规范化标题匹配最近 45 天，且主办方相同或活动同日时，关联已有活动，不重复生成候选。

运营已经整理好的活动使用[结构化导入](../操作手册/结构化活动导入.md)：`POST /api/events/import` 复用正式创建、审核和归属链，默认待审核，来源重复返回已有 ID，无需重新抓取和 AI 提取。未知日期、积分保留为空；先查来源再存封面，创建前失败清理临时文件，入库后的失败保留诊断依据。

网页、文档、[CLI 投稿](../操作手册/AI社区CLI投稿.md)和采集使用同一正式内容规则，不各自建立内容池。

### 来源能力与限制

- 公众号后台来源沿用现有登录、账号、运行与恢复机制，授权有效与文章可抓取分别判断。
- WeWe RSS 是独立服务，主平台经后端代理管理和读取，不持有读书 Cookie。
- `weread_mp` 读取独立采集器的本地最新文章缓存，与旧来源并存。它提供最新文章入口，不保证完整历史，也不保证一次群发的全部次条。
- 可选搜索补抓按文章 `biz/mid/idx` 在发现头条后第 12、48 小时查找同组次条；仅经公开原文页补抓，搜索收录不完整，不把缺少结果当作原文不存在。

### 正文与图片处理

真实正文不足时保持短摘要或待处理，不补造内容。普通图文读取正文节点，图片消息读取明确图片列表与描述元数据，不执行原站脚本、不把分享封面或水印当正文。

视觉后处理使用本地文章图片进行分片 OCR 和原图配图评分，只补充机器识别文本和封面，仍走既有候选审核。缓存按内容比较幂等应用，重新导入正文后可以恢复识别结果；内容未变时不重写记录、不重置提取状态、不重复调用模型。

活动正文先显示主图，再显示看点、关键信息与分节要点，末尾最多放 3 张有用海报/照片，排除二维码和 Logo。卡片摘要独立保存；星期由代码按日期计算，多场次或地点逐行表达，动态封面缩略图保留动画。

## 交互设计

后台区分来源管理、采集运行、文章、解析/审核和配置等工作区；新读书缓存采集器有独立管理入口，保留原采集界面。业务状态来自服务端，不由浏览器是否仍打开决定任务完成。

管理员可以查看来源是否有效、卡在哪个阶段、已处理多少、失败原因及恢复操作；扫码授权、采集启动、候选审核和正式发布分别反馈。诊断显示可操作错误和进度，不返回 Cookie、私有模型地址或图片 data URL。

正式内容编辑保留来源链接和原发布主体，修正时间、主办方、归属或正文时不破坏既有审核记录。重复来源明确跳到已有文章或活动；暂停、重试和清理不能静默删除未发布的人工修改。

应验证真实来源的登录、正文、图片、提取、审核、发布与失败恢复；只有一个可用账号时不能宣称多账号分配已通过。具体缺口在状态文档维护。

## 技术设计

### 运行与存储

`wechatMpAdminService`、`wechatReadRssService`、`wechatReadRssAdminService` 和 `wechatMpScheduledIngestService` 承载现有来源。`deploy/weread/weread_poll.py` 在独立容器读取授权并持久化最新索引、正文和重试状态；`wechatWereadCacheService` 读取清洗后的缓存并复用图片本地化，`wechatWereadAdminService` 提供状态、控制与扫码代理。

`WEREAD_INGEST_INTERVAL_MINUTES` 开启不少于 5 分钟的缓存导入，旧来源保留每日调度；开发环境遵循后台任务关闭设置。只导入正文就绪的缓存，发布时间缺失时可用原文 `ct` 补足。

内部文章 token 的 `~` 转成公开短链接 `_`，内部 ID 不变。刷新旧链接时识别同来源记录、保留文章及候选 ID，同步仍指向旧链接的候选，不新增重复记录。

`wechatArticleVisionService` 通过统一私有 AI runtime 处理本地图片，缓存位于私有 `server/data/wechat-vision`；`WEREAD_VISION_ENABLED` 控制开关，有限预算跨轮恢复。活动正文由 `server/src/utils/wechatEventSummary.js` 统一排版。模型政策遵循[主蓝图](../产品蓝图.md#搜索与-ai)，正文 OCR 不绕过它。

### 出站与数据保护

`wechatRequestPolicy` 校验主机、凭据、协议、端口与重定向，文章及图片使用明确受信来源。公开正文回退带已验证的请求头，同时限速、限制响应大小并拒绝验证跳转；仅标题、成功退出码或 HTTP 成功不作为正文成功证据。

采集账号、密钥、私有缓存、文章运行数据与备份不进入 Git 或对外诊断。采集器拥有授权，主平台只使用受控 API/缓存；浏览器不直接获得采集凭据。

### 独立 RSS 服务交付

WeWe RSS 在独立仓库构建、测试并发布固定摘要镜像，主平台通过 `WEWE_RSS_BASE_URL` 与后端授权代理访问。生产使用成品镜像，不现场构建；保留 Compose、私有配置、数据库、外部卷与备份，运行镜像不包含应用源码、测试和 source map。

继续沿用 `wewe-rss-beta` 项目及既有数据库卷，资源上限为 512 MB 内存、0.5 CPU、128 PID、Node 堆 320 MB，日志 10 MB × 3。Feed 默认元数据模式，健康检查使用根入口或单条元数据。更换镜像前备份数据库并保存旧镜像；失败回退应用，不自动恢复数据库。

部署细节查[采集手册](../操作手册/微信公众号文章采集.md)及[读书采集器说明](../../deploy/weread/README.md)，不把某次镜像摘要或真实账号数量写成永久产品要求。
