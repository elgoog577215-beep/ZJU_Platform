## 1. 产品定义

拓途浙享是**拓浙 AI 生态的数字底座与公共入口**。它围绕浙江大学及相关创新网络，把校园机会、AI 学习、社区协作、实践项目、浙客松赛事、人才与组织身份、成果记录和产学连接放进同一套可发现、可参与、可沉淀、可治理的系统。

平台的核心价值不是“多放一些内容”，而是减少四类断裂：

1. 信息存在，但合适的人看不到。
2. 人彼此可见，但缺少可信身份、项目和组织关系。
3. 学习、活动和赛事发生了，但没有形成持续项目与个人成果。
4. 企业、学院和学生发生了一次合作，但过程、人才和结果无法复用。

### 1.1 产品与生态的关系

拓浙 AI 生态是母系统，拓途浙享是数字平台。平台负责触达、连接、记录和运营，不独自承包生态中的线下组织、商业合同、企业交付或学校管理职责。

公开品牌统一使用“拓浙AI生态”。全站导航、Logo 文字、SEO、页脚、分享物料和用户入口先表达生态身份；只有在需要区分数字产品与线下组织、商业交付或学校职责时，才使用“拓途浙享”说明数字平台载体。域名、包 ID、历史接口和内部工程标识可以继续沿用 `tuotuzju`，但不得再把“数字艺术与科技”“信息聚合平台”作为网站总定位。

```text
生态资源与真实需求
-> 拓途浙享公开触达、匹配和组织
-> 社区学习、活动参与、项目实践与赛事验证
-> 身份、过程、作品、成果和关系沉淀
-> 人才识别、组织协作和下一轮机会
```

### 1.2 核心用户

| 用户                 | 核心任务                                           | 平台给出的正式价值                         |
| -------------------- | -------------------------------------------------- | ------------------------------------------ |
| 学生与青年开发者     | 发现机会、学习、组队、做项目、展示成果             | 可信身份、个性化机会、项目履历和持续连接   |
| 社团、学院与校园组织 | 发布活动、组织成员、维护主体、沉淀历史             | 认证主体、内容归属、成员协作和影响记录     |
| 企业、政府与合作伙伴 | 发布真实问题、找到团队、观察人才和结果             | 清晰合作身份、项目入口、赛事成果与人才线索 |
| 生态运营者           | 审核内容、治理主体关系、运营赛事项目、管理 AI 能力 | 统一治理控制台、审计、质量和恢复能力       |
| 普通访客             | 了解生态、发现活动内容与优秀项目                   | 无需先理解组织结构即可进入有价值的公开信息 |

### 1.3 北极星

北极星不是页面访问量，而是**产生并沉淀的有效连接**：用户从平台发现机会或伙伴，发生可验证的参与、协作、项目或成果，并能回到明确的人、组织、活动、项目和赛事记录。

可以用以下证据判断有效连接：

- 用户收藏、报名、投稿、加入项目或确认组织关系。
- 项目完成招募、更新状态、形成作品或赛事成果。
- 活动、内容和成果明确归属到认证主体。
- 推荐与搜索带来后续行动，而不只是曝光。
- 一次合作能产生下一次项目、人才或内容复用。

### 1.4 明确不做

- 不做泛校园门户、教务系统或学校行政系统。
- 不做以私信、关注数和无限信息流为中心的通用社交网络。
- 不做独立在线教育 LMS；学习资源服务实践与社区，不扩张成课程管理平台。
- 不在本平台内承载企业合同、付款、法务、商业交付和融资管理。
- 不为每个栏目建立独立账号、身份、内容、审核或 AI 系统。
- 不因存在 Android、iOS、微信和 Web 就重写多套产品。

## 2. 两条核心闭环

### 2.1 用户成长闭环

```text
发现活动、内容、组织或项目
-> 搜索、推荐与主页建立理解
-> 收藏、报名、投稿、组队或参与
-> 在社区、项目或赛事中行动
-> 形成内容、作品、成果与关系证据
-> 回到个人/组织 profile 和下一次机会
```

用户成长闭环要求所有入口都能回答：用户下一步能做什么，行动结果由哪个正式对象保存，之后怎样再次找到。

### 2.2 生态转化闭环

```text
学校、组织、企业与真实需求进入
-> 内容、活动、项目或赛事承载
-> 社区聚人、项目育人、赛事选才
-> 过程与成果接受治理和公开展示
-> 人才、组织与合作关系沉淀
-> 形成下一轮需求、资源和机会
```

生态转化不是把合作方 logo 放在页面上，而是让主体、需求、参与、项目、成果和后续关系都能被系统明确表达。

## 3. 产品空间

### 3.1 首页与 About

- 首页负责让用户快速理解“这里有什么值得进入”。
- About 负责解释拓浙 AI 生态是什么、谁在支持、怎样运行以及如何参与。
- 官网以拓浙AI生态为主语，但必须明确网站是生态的公共入口与数字底座，不能把网页能力等同于全部线下组织、商业交付或学校职责。
- 品牌页不能把生态讲成若干栏目列表；它应解释资源怎样进入、怎样转化为学习与项目、怎样形成成果与下一轮合作。

### 3.2 活动与机会

- 活动页承载校园机会、学院范围、类别、时间地点、组织归属与报名行动。
- 全站搜索帮助用户主动找资源；活动推荐助手结合画像、行为和本次意图帮助用户做机会决策。
- 活动推荐画像归用户系统维护，推荐界面不另建长期资料表单。

### 3.3 AI 社区与学习资源

- AI 社区是统一内容系统，公共版面为技术分享、求助问答、新闻热点和组队协作。
- 学习资源采用“资料用途栏目 + 课程、教师、学期等元信息精筛”。
- 网页编辑、文档导入、CLI 投稿和微信公众号采集进入同一发布、审核和归属链，不形成平行内容池。
- 微信群和社群二维码是辅助连接目录，不是社区主内容系统。

### 3.4 项目广场

- 项目是一等产品对象，不是一次性组队帖子或个人主页装饰卡片。
- 项目名片表达目标、阶段、需要的人、发起主体、进展和成果。
- 项目广场负责发现，个人与组织主页负责归属，收藏和分享负责传播，后台负责治理。
- 项目可在多届赛事中反复参赛；项目广场保存长期成长事实，每届赛事成果只保存当届快照、奖项和证据，并通过显式关系回到项目。

### 3.5 浙客松与成果

- 浙客松同时承担真实问题验证、人才识别、跨学科协作和品牌传播。
- 多场赛事复用同一页面模板与运营框架，但各自拥有稳定 `event_key`、时间轴、报名表单和成果档案；后台发布配置后，前台、报名和成果链读取同一份赛事事实。
- 报名、赛事、作品、照片、视频、荣誉和成员归属属于同一成果体系。
- 赛事现场、当届项目广场和影像档案是同一赛事上下文的三个入口，分别承载总览、作品发现和现场证据，不复制彼此的业务真源。
- 赛后成果不是报名页附属内容；历史媒体不能在依赖未确认时破坏性迁移。

### 3.6 人、组织与数字名片

- 账号负责登录和权限，profile 负责公开身份、组织主体与内容归属。
- 个人、社团、学院、学校、企业和其他组织共享 profile 模型，但公开范围和管理权限不同。
- 数字名片是 profile 的传播层，不新增身份源；个人主页和组织主页是完整信息与成果载体。
- 公共组织目录不批量枚举自动生成的个人账号主体。

### 3.7 媒体与记录

- 图片、视频、音频和文章既可以独立展示，也可以成为活动、赛事、项目和主体的证据或表达。
- 媒体库不替代业务对象；作品、活动和项目不能只靠标签或文件名建立关系。

### 3.8 运营与治理后台

后台是生态运营控制台，按任务组织为：

1. 运营总览。
2. 内容与审核。
3. 主体与关系。
4. 生态项目运营。
5. AI 能力治理。
6. 系统与审计。

后台不能继续只是历史页面和通用 CRUD 的集合，也不能把尚未闭环的 AI 能力包装成完整智能治理。

## 4. 领域真源

| 领域     | 正式拥有者                                                            | 允许的投影                               | 不能成为第二真源的对象                       |
| -------- | --------------------------------------------------------------------- | ---------------------------------------- | -------------------------------------------- |
| 登录账号 | `users`                                                               | 登录态、账号概览、后台用户列表           | profile 页面本地副本                         |
| 公开主体 | `profiles + profile_members + profile_aliases`                        | 个人/组织主页、目录、名片                | 单独的组织账号体系、内容内自由文本主体       |
| 权限     | `account_type + review_permission + role/admin_scope`                 | 前端按钮与后台分区                       | 一个万能 `role` 字段                         |
| 合作关系 | `ecosystem_partners.partner_scope`                                    | About、黑客松、活动组织墙                | 根据 profile 存在、logo 或活动数量推断合作方 |
| 活动     | `events` 及显式发布/主办 profile 关系                                 | 活动页、搜索、推荐、日历                 | 微信解析草稿、页面筛选状态                   |
| 社区内容 | `articles`、`news`、`community_posts` 的当前兼容合同                  | AI 社区统一内容视图、用户投稿管理        | CLI、微信采集或微信群的独立内容池            |
| 项目     | `project_cards` 及发起主体关系                                        | 项目广场、主页项目、收藏、分享海报       | 组队帖、自定义卡片、海报图片                 |
| 赛事成果 | 赛事日程模板、报名、canonical competition、work、media 与成员归属对象 | 浙客松赛事页、成果页、个人成果、媒体展示 | legacy `competition_media`、静态演示数组     |
| 搜索     | 公开已审核资源 + `resource_search_index`                              | 全站统一结果协议                         | 浏览器缓存、模型临时回答                     |
| 推荐     | 用户画像、活动事实、行为证据和推荐遥测                                | 活动助手建议与解释                       | AI 对用户身份或长期偏好的无依据猜测          |
| 微信采集 | 采集账号、运行进度、文章、解析草稿、AI 初筛和审核结果                 | 后台任务视图、活动候选与自动治理         | 浏览器会话、单次抓取日志                     |

当前社区底层仍有多表兼容，这是待收束实现，不代表产品允许多个独立社区。

## 5. 身份、归属与权限模型

### 5.1 三轴权限

- `account_type`：个人或组织等账号主体类型。
- `review_permission`：普通审核、免审核或更高发布能力。
- `role/admin_scope`：后台访问与管理范围。

组织账号不自动是管理员，免审核不自动拥有后台，合作展示身份也不自动改变账号权限。

### 5.2 多主体归属

一条活动、内容、项目或成果可以同时关联：

- 上传者或操作者。
- 对外发布主体。
- 主办或合作主体。
- 历史归属和成员关系。

这些关系通过显式字段和关联表表达，不复制业务记录。历史归属迁移必须有候选、证据、人工确认和审计。

## 6. AI 能力边界

### 6.1 搜索与推荐分工

- 全站搜索回答“我主动想找什么”，覆盖活动、AI 社区、媒体等公开资源，并保持统一结果协议。
- 活动推荐回答“结合我的长期资料和本次意图，哪些机会更适合”，保留独立画像、排序、解释、反馈和评测链。
- 两者可以共享 AI runtime、模型配置和遥测，但不能合并产品入口或数据责任。

### 6.2 AI 治理要求

每个 AI 能力必须说明：

- 输入来自哪些正式事实。
- 输出是搜索条件、建议、草稿还是正式对象。
- 谁确认、谁写入、怎样审计。
- provider 失败、结构非法或质量不足时怎样降级。
- 如何做 golden、live、压力与长期效果验证。

AI 不替代权限、审核、主体归属和正式业务写入。轻量词元索引不能宣传成 embedding，规则扫描不能宣传成完整智能治理。

## 7. 多端边界

- Web/PWA 是主要产品与代码真源。
- 微信小程序、Android 和 iOS 复用同一业务能力、身份、审核和 API。
- 上传、分享、登录、复制、外链等平台能力在同一用户入口内部按运行时分流。
- 原生壳只补安全区、键盘、返回、分享、上传、登录持久化和平台桥接，不复制页面与业务状态。
- 多端完成度必须分别验证，Web 构建成功不代表微信、Android 或 iOS 真机通过。

## 8. 异常与降级

| 场景               | 正确行为                                      | 禁止行为                                 |
| ------------------ | --------------------------------------------- | ---------------------------------------- |
| AI provider 不可用 | 保留原始输入与上次有效结果，明确失败并可重试  | 伪造成功结果或静默写正式对象             |
| 微信采集失败       | 保存运行、文章状态、失败原因和恢复动作        | 把登录态、抓取成功和内容发布压成一个状态 |
| 组织归属不确定     | 形成候选并人工确认                            | 只凭名称或地点自动迁移所有权             |
| 复制权限被拒绝     | 提供可选择的手动复制内容                      | 只显示“复制失败”Toast                    |
| 移动弹层异常       | 保持最后页面，修复 portal、返回和 scroll lock | 只无限提高 `z-index`                     |
| 新版本静态资源失配 | 有界清理旧 chunk 缓存并只重载一次             | 无限刷新或让根 Service Worker 接管子应用 |
| 数据迁移失败       | 事务回滚、保留备份和迁移记录                  | 在热请求 controller 中临时改表掩盖问题   |

## 9. 长期建设顺序

`P0-P5` 表示产品与工程依赖，不等于当期任务优先级。当前主攻只看[产品状态](./产品状态.md)，具体施工只看活动 OpenSpec。

| 层级          | 核心问题                                             | 完成标志                                                 |
| ------------- | ---------------------------------------------------- | -------------------------------------------------------- |
| P0 可信底座   | 身份、数据、权限、迁移、审核、隐私和部署是否可靠     | 正式真源明确，迁移可回退，公开仓库无敏感材料，生产可验证 |
| P1 发现与内容 | 活动、社区、资源和搜索是否统一可发现、可投稿、可治理 | 内容入口共享审核归属，搜索推荐各自闭环，旧内容心智退出   |
| P2 人与组织   | 用户、profile、合作方、成员和历史归属是否一致        | 三轴权限稳定，主体关系可审计，公开目录不泄露内部账号     |
| P3 项目与赛事 | 学习和连接能否转化为项目、作品和人才证据             | 项目广场与浙客松从发现到成果形成完整纵向闭环             |
| P4 生态运营   | 运营者能否在一个控制台管理内容、关系、项目和 AI 能力 | 后台按任务重排，指标、异常、审核和恢复有清晰所有者       |
| P5 多端与扩展 | 同一产品能否稳定进入微信、Android、iOS 和外部协作    | 多端复用同一合同，真机通过，平台差异不制造第二产品       |

## 10. 产品完成门

只有同时满足以下条件，才能把拓途浙享称为成熟的生态数字底座：

1. 用户能从机会发现进入行动，并把行动沉淀为个人、组织、项目或赛事成果。
2. 内容、主体、关系、项目和成果都有唯一正式拥有者与可审计写入路径。
3. AI 搜索、推荐、采集和治理使用真实事实，可解释、可评测、可降级。
4. 运营者能从统一后台处理内容、主体关系、生态项目、AI 能力和系统风险。
5. Web、微信、Android 和 iOS 共享同一产品与数据合同，并分别通过真实环境验证。
6. 隐私、权限、迁移、缓存和部署失败不会破坏用户资产或伪造成功状态。
7. 平台能够提供持续的有效连接证据，而不只积累页面、栏目和访问量。

这些是终局完成门，不表示当前完成度。当前事实只看[产品状态](./产品状态.md)。
