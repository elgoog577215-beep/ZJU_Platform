## 社区抽奖

设计入口：蓝图[业务逻辑](产品蓝图.md#社区抽奖)与[技术实现](产品蓝图.md#抽奖运行)。

- 当前实现：黑客松报名旁提供赛事抽奖入口，按赛事配置官方推文、点赞门槛、奖品与时间；参与者填写点赞数并提交截图，赛事抽奖强制管理员审核，退回可补交，审核通过才进入名单。手机可直接打开赛事抽奖链接。发布后、原开奖时间前支持管理员直接保存配置，保留原报名及审核记录，记录修改前后配置和版本；到点、已开奖或已取消后禁止修改，开奖使用最新配置。每账号唯一编号、私有图片凭证、审核补交、自动开奖与重启补处理、编号公示、限时领奖、发放记录齐备；新建/编辑页面保存草稿后自动生成本期专属链接和二维码，可复制链接、下载 PNG，并提示草稿发布后页面才开放。
- 推广入口验证：本地浏览器覆盖新建保存、活动切换、复制和下载，含桌面白天及手机夜间布局；下载的 1024px PNG 已解码核对详情页地址。对应回归为 [lottery-share.spec.js](../e2e/lottery-share.spec.js)，不替代真实报名和审核验收。
- 发布后编辑验证：12 项后端测试覆盖保存权限、版本冲突、报名/凭证/审核保留、配置校验、到点锁定及最新奖品和门槛用于开奖；6 项浏览器测试覆盖已发布活动修改、保存后刷新、原推广链接和二维码保留，以及桌面白天/390px 手机夜间布局。浏览器保存使用模拟 API；真实 HTTP 保存与数据保留在独立测试数据库中核对，未修改生产活动内容。
- 既有记录：本地后端流程与权限检查通过；手机登录、图片上传和报名编号已有验证，后台配置与报名列表已显示。

## 内容采集

设计入口：[完整设计](功能设计/内容采集.md)。

- 既有记录覆盖独立 RSS 镜像、主平台连接及最新文章缓存接入；不把当时的来源数量、账号状态或镜像摘要当作当前运行事实。
- 仍需真实证据：有效 feed 的正文和图片、Atom/TRPC、后台模式切换、来源提醒、授权失效与异常恢复；多账号随机分配需至少两个实际有效账号。
- 微信读书缓存只提供最新入口；可选搜索补抓也不保证完整历史或每次群发的全部文章，这属于能力边界，不是通过一次回归就能消除的缺口。
- 视觉后处理与重复导入已有实现，仍应在后续相关任务中核对内容是否有来源、重复应用是否保持人工审核与原记录。
