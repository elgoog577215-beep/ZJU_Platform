# 本机中转部署

用于 GitHub 直传生产服务器很慢的情况。GitHub 仍承担代码真源、CI 和不可变构建；本机仅中转已验证的发布包，不上传工作区的未提交文件。

## 前置条件

本机有 Node.js、GitHub CLI（已登录且能读取本仓库 Actions）、OpenSSH，并已具备生产服务器 SSH 权限。服务器沿用现有 Node、PM2、Caddy、Playwright 和私有 `.env`。不把 SSH 密码、模型地址或 token 写入脚本或仓库。

前端依赖检查使用 `npm run audit:dependencies`。Tailwind 3 的构建依赖 `braces` 暂时固定到[上游深度限制修复](https://github.com/micromatch/braces/pull/72)的完整提交 `28d440b5dd449dbf1fe6f3506cf94ecca4d02660`，保留现有样式框架。补丁仍标记为 3.0.3，原始 `npm audit` 会继续报告 [GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm)。项目检查先核对锁定地址、归档完整性、实际代码哈希及字符串/AST 深度和循环保护，仅将这一条已修复告警及其依赖传播识别为已缓解；混合依赖树按叶子告警重新判断严重度，已修复高危与未修复中低危并存不再误判为高危，未知依赖、未知严重度和循环仍阻断；补丁不符、检查失败或出现其他高危告警时发布仍失败。上游正式发布修复版后应移除此临时固定和识别逻辑。

## 操作

1. 在 GitHub 仓库设置变量 `ZJU_DEPLOY_TRANSPORT=local`。这会保留 CI 构建和 release artifact，跳过 GitHub 直传部署。此模式下每次发布都需要从本机执行后续步骤。
2. 将改动通过 CI 后合入 master，等待 master 的 CI 完成，取得该次 run ID。
3. 从仓库目录运行：

    ```sh
    node scripts/deploy-via-local.mjs RUN_ID user@server
    # 已使用 SSH 多路复用时，可在后面传递 OpenSSH 参数：
    # -o ControlPath=/path/to/control-socket
    ```

脚本只接受当前 master 的成功 push run；下载 `release-<commit>`，校验 tar.gz 的 SHA-256 和部署脚本与该提交的一致性，经本机上传服务器后执行共用部署脚本。上传期间 master 改变会停止，避免部署过时版本。服务器私有模型地址直接从既有 `.env` 读取，不传回本机。

## 验收与回退

共用部署脚本先安装与发布包匹配的 Chromium 并实际启动检查；已具备系统依赖时不重复刷新系统软件源。仅当浏览器无法启动时补装系统依赖并再次检查，仍不可用则在切换线上文件前停止，保留原版本。

检查命令退出码为 0、服务器 `.deployed-release` 的 commit 与 GitHub 一致、HTTPS `/api/health` 返回成功，以及本次变更的真实用户路径。CI 在本机中转模式不会执行 GitHub 端的生产 smoke，因此不能用绿色 CI 代替本次线上验收。

部署互斥锁避免本机和 GitHub 同时切换文件。保留现有 `.env`、上传文件和数据库；切换或健康检查失败时自动恢复上一版应用。成功后的上一版位于 `.deployments/<commit>/previous`，保留到下一次部署。发布切换前使用 SQLite 一致性快照自动备份当前数据库（包含已提交 WAL），验证完整性，失败则停止发布；备份位于 `server/backups/pre-release-<commit>-<timestamp>.sqlite`，不会打包或上传。本次仓库字段为可空的增量列，旧代码回退后仍可使用原表；数据库不自动恢复，恢复快照前须核对备份后的新增报名，避免丢失新数据。

若需要回退正式版本，优先在 GitHub revert 变更，等待新 master CI 后再次中转发布。将 `ZJU_DEPLOY_TRANSPORT` 改回 `github`（或删除变量）可恢复后续 master 推送的 GitHub 直传；不会自动补发此前跳过的部署。
